# Direct-AI vs Translator-plus-Solver Eval Pipeline -- Sequential Planning (MDP) module

Part A pipeline for the "sequential planning" module type, built the same
way as the repeated-game module: every test case is generated by a script,
solved by a script (real dynamic programming), and graded by a script. No
manually written problems or answers anywhere.

## Setup

```bash
pip install -r requirements.txt
```

Create a `.env` file in this directory (both optional, sensible defaults):

```
OLLAMA_HOST=http://localhost:11434
OLLAMA_MODEL=llama3.2:3b
```

## Files, in build order

1. `generator.py` -- samples a random, well-formed 2-state ("Low"/"High")
   / 2-action ("Cautious"/"Aggressive") MDP: four immediate rewards and
   four transition probabilities, plus either a fixed integer horizon or
   "unknown" horizon + a discount factor. The reward/probability structure
   is constrained (Aggressive pays more now, Cautious better protects
   future access to the High state) so the scenario has a genuine
   short-term-vs-long-term tradeoff rather than an obviously dominant
   action -- the sequential-planning analogue of the repeated-game
   module's `T>R>P>S, 2R>T+S` convention.
2. `solver.py` -- computes ground truth: exact backward induction for a
   finite horizon, or value iteration to convergence on the discounted
   Bellman optimality equation for an unknown/indefinite horizon. Returns
   the optimal action for the current period from the starting ("Low")
   state, plus the Q-value margin between the two actions at the optimum.
3. `renderer.py` -- turns a scenario into a natural-language paragraph.
   Transition probabilities are displayed as rounded whole percents, and
   are sampled as whole percents in the first place, so the displayed
   number always matches the number driving the ground truth.
4. `test_case.py` -- combines 1-3 into `generate_test_case()`.
5. `direct_ai.py` -- Direct-AI arm: paragraph -> LLM -> extracted
   cautious/aggressive answer (no structure, no solver).
6. `translator_solver.py` -- Translator-plus-Solver arm: paragraph -> LLM
   structured JSON extraction (Pydantic schema + Ollama's structured-output
   mode) -> fed into the *same* solver from step 2.
7. `scoring.py` -- scores both arms against ground truth, with breakdowns
   by horizon type, Q-value margin at the optimum (near-threshold vs. not),
   and extraction validity.
8. `runner.py` -- runs N test cases end to end, prints a report, writes a
   full JSONL log.

`consistency_check.py` implements A10: renders 2-3 differently worded
paragraphs per sampled scenario and checks whether each arm's answer is
stable across wordings, independent of whether that answer is correct.

Test files (`*_test.py`) and `stress_test.py` use mocked/synthetic inputs
and require NO network access -- safe to run anytime to sanity-check logic.

## Running the real evaluation

```bash
python3 runner.py --n 20 --seed 42
```

Start at n=20 as a sanity check before scaling to several hundred. Use
`--sleep 1.0` if you're running against a shared/remote Ollama instance.

```bash
python3 consistency_check.py --sample-size 30 --variants 3 --seed 42
```

Output:
- Console: per-case pass/fail as it runs, then the aggregate report.
- `run_log.jsonl` / `consistency_log.jsonl`: one JSON record per test case
  / per wording -- use this to read exactly which paragraphs tripped up
  which arm.

## Known limitation carried over from the repeated-game module's design

Every scenario originates from a known generative structure (2 states, 2
actions). This measures recoverability and robustness to controlled
synthetic messiness, not the full unbounded variety of real human phrasing
or larger/messier planning problems. Part C scales this same pipeline to
the belief-updating module type; a richer state/action space for this
module is future work beyond Part A's scope.
